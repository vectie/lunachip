# PRX100 JTAG launch and polling experiment — 2026-10-18

Sequential launch dispatch reduces the measured median application time by
**8.6%**, with **24 fewer API calls** in the typical campaign. All compared
outputs match the CPU reference. Native checks: moon info/fmt, native deny-warning check and all **1,225 tests pass**; all16 re-exported hardware files match exactly.

The experiment changes host dispatch only, using the same qualified
FPDDR1.3Q bitstream and Qwen3-0.6B layer-zero q_proj channels 0–7, K=1024,
with three BF16 activation vectors from token IDs 42, 100 and 1000. The
independent CPU reference rounds each product and ordered sum to FP32.
Integer and first-party floating-point hardware remain unchanged.

See [the launch contract](../PRX100_JTAG_LAUNCH.md) for ordering, response
visibility, polling, timing boundaries and audit requirements.

Five fresh interleaved campaigns per prior `list` and candidate `joined`
profile ran on the same physical board and bitstream. Each campaign includes
106 projections / 848 output words: K=1,2,3,16,1023,1024; six repeated full
three-job batches; one-,18-,48-job batches; explicit cache invalidation and
cold reload. Thus each measured profile checks530 projections /4,240 outputs;
the comparison checks8,480 outputs. A separate final joined qualification adds
106 projections /848 exact outputs. Two earlier pilots are retained and
excluded from these statistics. All samples, including outliers, are retained.

Application reduction is8.63% (1.094×); summed resident reduction is9.82%
(1.109×); configuration-through-DONE reduction is10.44% (1.117×). The latter
sums `config_us + launch_poll_us`: descriptor work moves between those columns,
so comparing `launch_poll_us` alone would be misleading. All five paired
resident sums improve. Application pair2 regresses417.597→421.396 ms, and all
ranges overlap. These are measured medians, with no established tail or
statistical-confidence claim.

The preceding FPR report's historical48-job selected median was16.567 ms,
below this session's18.412 ms candidate median. This session's fresh baseline
is22.823 ms. Cross-session timings vary substantially; the reported gains use
only the fresh interleaved comparison and do not establish monotonic speedups
across historical reports.

Warm repeated control improves only0.95%. The48-job control median regresses
10.114→10.271 ms, despite its lower complete-batch median. Its result-readback
implementation is unchanged; the measured complete-batch gain cannot all be
attributed to launch dispatch. Four of five candidate runs require a second
48-job poll, included in every reported timer. The combined short-batch first
polls all observe DONE; busy retry behavior is additionally checked by negative
controls. This experiment reduces command invocations, not the number of
hardware status observations.

The upload remains22,528 bytes. Every campaign reads17,796 DDR words and

results and guards. Each completion still reads every output and all34 counter

BRESP and optional RRESP are checked; per-descriptor response visibility is
not claimed. The separate CPU audit verifies publication order, observed DONE,
error zero, all output bits and every counter invariant.
