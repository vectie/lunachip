Accelerator a10 MIG source-to-effective audit, 2026-10-26

The narrow-burst setting change is acceptable as an explicitly recorded Vivado capability propagation. It does not require a rebuild for this setting alone. Acceptance must bind both the original and effective input hashes, the generated IP sources, the unchanged routed checkpoint, and a fresh successful finalization. This is a semantic configuration change, not whitespace; the failed earlier finalization preflight remains preserved.

The source MIG project is the accelerator input in sealed ready-inputs a5, SHA-256 `4c91feaa730501267aacb001f22b12eefb2e7f5aaaa3e6bbb3904595c96d285a`. The actual read-only project probe observes XDMA narrow metadata0, accelerator master metadata1, crossbar M00 metadata1, and MIG metadata1. The accelerator wrapper specifies AXI4, DATA_WIDTH128, ADDR_WIDTH32, ID_WIDTH0 and MAX_BURST_LENGTH1 but does not explicitly specify narrow-burst metadata. The observed default1 consequently requests conservative downstream support. This metadata path and the installed callback explain the effective XML. Existing earlier build `transport-properties.txt` and `resolved-design.tcl` already recorded MIG narrow support1 before synthesis; this is not a new routed-design modification.

MIG remains ADDR_WIDTH31, DATA_WIDTH128 and ID_WIDTH5. DDR is MT41K256M8, DQ64/DQS8, row15/column10/bank3, tCK1250ps, nCK_PER_CLK4. The capacity is 2^(15+10+3)×8 bytes = 2GiB. Source/effective/generated XML equivalence preserves all remaining geometry, rank, pin and timing settings. The mapped checkpoint independently confirms the 31-bit AW/AR addresses, 128-bit W/R data, 16 strobes, all four 5-bit ID channels, DDR address15/bank3/data64/DQS8 pin counts. The checkpoint SHA-256 stays `e4dba7c1bd8553ca467c74f3e83a71c73ea9e6e447163e4c5f600bf965f9cbc2` before and after the probe.

The generated RTL explicitly sets `C_S_AXI_SUPPORTS_NARROW_BURST=1`. Its memory-controller interface is 2×4×64=512 bits, and `axi_mc` selects its upsizer whenever the external AXI width is smaller: `P_USE_UPSIZER=(C_S_AXI_DATA_WIDTH<C_MC_DATA_WIDTH)?1:C_S_AXI_SUPPORTS_NARROW_BURST`. Thus 128<512 already selects the upsizer independently of this flag. The mapped checkpoint contains `u_axi_mc/USE_UPSIZER.upsizer_d2`. The optimized checkpoint does not retain a distinct public configuration flag proving0 versus1 independently of its generated-source provenance; its mapped structure and source dependency are bound instead. This review does not claim bit-for-bit equivalence of separately synthesized alternative configurations.

The LunaChip bridge issues aligned 16-byte transfers with AW/ARSIZE4, AW/ARLEN0 and INCR. The actual routed master SIZE and LEN bits were checked against GND/VCC drivers, proving those constants after implementation. Scalar writes select one four-byte lane with strobes000f/00f0/0f00/f000; line writes useffff. These are byte enables within a full-width AXI transfer, not narrow-burst sizes. The remaining bytes are preserved by WSTRB. The canonical bridge, its emitted wrapper, existing masked-write replay and formal assertions cover this protocol. Narrow-burst capability1 does not invalidate this traffic. AMD's [UG586 AXI parameter options](https://docs.amd.com/r/en-US/ug586_7Series_MIS/AXI-Parameter-Options) describes disabling the support as an optional logic-saving optimization; its [slave parameter definition](https://docs.amd.com/r/en-US/ug586_7Series_MIS/AXI4-Slave-Interface-Parameters) states that enabling it supplies support for narrow transfers. AMD's [AXI metadata definitions](https://docs.amd.com/r/en-US/pg373-axi-register-slice/Advanced-Settings-Parameters) distinguish transfer size from bus width and describe conservative master metadata defaults.

The exact tested public-property loop is retained as `effective-interface-assertions.tcl`, entry `pblaze_assert_mig_effective_interface report`. It requires the project and block design to be open, before closing the BD and opening the routed run. Its body was extracted verbatim from the successful actual probe. The complete actual probe also performs mapped pin/constant checks and source hashes; no synthesis, route, source restore or hardware action occurred.

Future generation should pass an isolated writable MIG project copy to Vivado, preserve the exported input, and record source/effective identities. For the present accelerator profile, permit only this exact single-tag0→1 transformation, assert the effective metadata and all other bytes, and require smoke input equality. Any broader difference must fail. Choosing explicit narrow metadata0 as a resource optimization would be a separate freshly implemented configuration, not a reason to change the already reviewed route. Real DDR-chip identification and physical-board operation remain outside this configuration proof.
