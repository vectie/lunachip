# PRX100 polling and diagnostic overhead — 2026-10-18

Reusing validated completed-counter cache evidence and pacing longer batches
reduces median resident 48-job completion from **22.428 to 19.370 ms**
(**1.158×**, 13.635% less time). Complete application time, including upload,
both actual operand readbacks and 106 projections, changes **435.145→403.664
ms** (1.078×). Five interleaved runs of each profile pass **530 projections /
4,240 bit-exact CPU-reference outputs**. Ranges overlap and one resident pair
regresses slightly; these are measured medians, not a latency guarantee.

The selected host profile is `paced`; `certified` exposes cache-evidence reuse
without delay and remains available. Its warm repeated-job median is better
in this sample. Pacing adds only a 1.020× resident-batch median ratio over
cache reuse alone, so a meaningful incremental pacing speedup is not established.
The primary demonstrated change is eliminating fourteen redundant singleton
cache reads. Both alternatives preserve full output/error/counter checks.

## Changes and correctness boundary

The [polling contract](../PRX100_JTAG_POLLING.md) defines the six `.mbtx` entry
points: `prx100-fps-{board,audit,groups,metrics,policy,close}`. The existing
completed 34-word snapshot includes cache-valid at byte address 108. After all
results, counters and error checks pass, its raw transaction sequence can serve
as the next prelaunch cache certificate. DDR/base/control writes and START
revoke it; changing only K/job/vector descriptors preserves it. The first cold
batch and the explicitly invalidated final cold batch still read cache directly.
This changes sixteen singleton reads to two, with fourteen exact prior snapshot
references recorded in `cache-evidence.tsv`. Exclusive target ownership is required.

The paced profile waits after acknowledged START before its first status/error
poll. The bounded formula uses arithmetic work and half the previous measured
poll round trip; it requests 0–10 ms and normally delays the 48-job case by
about 2 ms. `polling.tsv` records requested and actual time, both included in
the launch/complete wall timers. Expiration of a delay never means completion:
the driver still requires observed DONE=5 and error=0, then every output and
all 34 counter words. The original bounded polling loop remains active.

The fixed FPDDR1.3Q bitstream, integer core, FP arithmetic, controller, bridge,
vendor IP, 50/100 MHz core/UI and DDR layout are unchanged. CPU_TAG cable
`ME10E06D1010A` runs at 30 MHz; each programming checks FPGA identity, source/
bit qualification, configuration DONE/CRC and runtime read/write queue depths
of sixteen. Programming is volatile; flash is untouched. No CAD rebuild is needed.

DDR queues retain at most sixteen homogeneous bursts, at most 256 words each,
without 4 KiB crossing. `GROUP_OKAY` means the observed final group response;
individual queued AXI responses are not established. Every input and output
word remains independently checked. This optimization does not reduce the
diagnostic payload or skip result readback to obtain a lower timing.

An independent scalar reference reconstructs BF16 operands and installed
descriptors from raw DDR/MMIO writes, then uses separately rounded FP32
multiply and increasing-K FP32 accumulation. Every result DDR read, table
word and final counter-mirrored result must match exactly. Each campaign
covers K=1,2,3,16,1023,1024; six repeated full three-job batches; warm 1/18/48-job
batches; and a final cold three-job batch. That is 91 full and 15 prefix
projections, yielding 848 outputs per campaign.

Complement poison is written and fully verified before every actual operand.
Actual operands are fully read before and after jobs: two writes and three
readbacks per model word. All 24 boundary guards, scratch, cache, completed
index/vector, staged/loaded/read/write counts, overlap accounting, prepared/
started/retired/pending drain and errors are checked. Seven invalid bulk
operations are rejected locally; five invalid device accesses return SLVERR.

Prespecified interleaving is compact1,certified1,paced1,paced2,certified2,compact2,
certified3,compact3,paced3,compact4,paced4,certified4,paced5,compact5,certified5.
Each of these fifteen campaigns passes independent CPU, group, phase-timing
and cache/polling-policy audits on Linux and macOS: **60 JSON pairs are
byte-identical**. Two exploratory pilots and one subsequent full paced board
qualification are retained and excluded from statistics. The final qualification
also passes all four Linux audits. CAD is idle during physical measurements.

Twelve offline negatives reject poison corruption, consistent raw/table result
corruption, an oversized queue, inconsistent timing, a nonzero coalesced error,
a stale descriptor, missing DONE, reuse after explicit invalidation, an old
snapshot reference, an inconsistent delay, and intervening base/DDR writes.
No negative emits a PASS receipt. The last two synthetic fixtures deliberately
rebind the CPU raw digest solely to test policy rejection beyond source binding;
they are explicitly marked as unsuccessful CPU-audit fixtures.

Application/single/48-job statistics have five samples each; repeated three-job

Pacing is selected by the lower measured five-run 48-job median, with both
alternatives and all observations retained in `selection.json`. This is empirical

repeated-job median by 24.709%; the paced profile improves it by 14.629%.
The profiles use the same short-batch code with zero requested delay; differences
between their short-batch medians do not establish a causal pacing penalty.

Median pacing requests total 2 ms per campaign, range 1–3 ms. Median total
status polls change 17→16, range 16–18 baseline versus 16–17 paced. Fourteen
cache calls and approximately one poll disappear, while full result/counter
