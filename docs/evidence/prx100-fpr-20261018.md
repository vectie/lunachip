# PRX100 result-readback overhead — 2026-10-18

Combining full DDR result reads and the required 34-word counter snapshot in
one command reduces the selected mode's median 48-job readback phase from
**10.099 to 7.950 ms** (**1.270×**,21.279% less time). Median complete resident
48-job time changes **20.597→16.567 ms** (1.243×,19.566% less time). All five
resident/readback pairs improve. Five interleaved campaigns per profile each
pass **530 projections /4,240 bit-exact CPU-reference outputs**.

The selected mode is **`list`**, sequential multi-transaction dispatch inside
one `run_hw_axi` command. Hardware-queued `fused` dispatch is also retained.
Their large-batch readback medians differ by only26 µs; this does not establish
meaningful queue-versus-list superiority. List mode is chosen after review
because its full resident completion is lower in this sample. Application
medians differ only2.8%, with broad overlap; a meaningful application-wide or
tail-latency improvement is not established.

Integer and all FP hardware remain unchanged. The existing FPDDR1.3Q bitstream
is reused; there is no synthesis/place/route rebuild.

## Implementation and equal payload

The [readback contract](../PRX100_JTAG_RESULT_READBACK.md) defines the
`prx100-fpr-{board,audit,groups,metrics,policy,close}.mbtx` entry points. The
baseline is the preceding paced/cache-evidence driver. The `fused` and `list`
modes combine the same one/two result bursts and counter burst into one
completed-read command after observed DONE=5,error=0. Outputs remain actual
DDR reads; no repeated-vector reconstruction or MMIO-result substitution is used.

Each campaign transfers **848 DDR output words plus544 counter words**, including
the snapshot's eight mirrored final results in every batch. Total DDR read/write
word counts remain **17,796/11,292** in every one of the fifteen matched runs.
Full model poisoning/readbacks, all guards, cache evidence, descriptor reuse,
bounded pacing, status/error polling and exact counter checks are retained.

Sixteen completed-read commands replace thirty-two calls per campaign. The
33 underlying result/counter transactions are unchanged:17 DDR result bursts
and16 counter bursts. Group totals change11→26 because sixteen combined groups
replace the previous grouped48-job result read, alongside ten unchanged input
groups. Combined read groups cover **143 transactions** overall, with22 read
groups /18,288 words and4 write groups /11,264 words. Every burst remains
at most256 words and within4 KiB; completed-read groups contain only2–3 reads.

The helper admits only full result ranges for1–48 jobs followed by exactly34
counter words at byte address48. Its phase guard requires observed completion.
The independent group audit checks the immediately preceding successful
status/error read, exact result coverage for that batch, counters last, full
group coverage, word totals, bounds and timing. The CPU audit independently
checks every DDR result and counter mirror against reconstructed operands;
the cache-policy audit binds the final counter transaction to subsequent cache
evidence. Generic DDR bulk transfers still reject MMIO.

The pinned local Vivado help documents queued and ordinary multi-transaction
dispatch. `list` runs transactions sequentially inside one command; it is not
hardware-queued completion. Legacy `queues.tsv` and `queued_*` timing fields
count these command groups too. `completed_read_dispatch` records the actual
mode. `GROUP_OKAY` means the observed final group/command response, not each
request's individual response; the final request is the counter burst. Full
data/CPU checks do not establish per-request queued error reporting. Command
errors remain enabled and no error-ignoring `-quiet` option is used.

## Performance

Combined readback time is `results_us + counters_us`, including result
retrieval/comparison and counter retrieval. In the combined modes, counters
are fetched inside the results phase; its subsequent counters phase is almost
empty. Comparing one phase alone would be misleading. Total resident time
starts before configuration/cache handling and ends after all checks, including
actual pacing delay. Application time includes the actual22,528-byte upload,
both actual input readbacks,106 projections and final guards. Qualification
also includes poison/initial checks. Startup/programming are excluded.
