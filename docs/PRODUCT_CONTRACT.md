# LunaChip product contract

## Product statement

LunaChip is one MoonBit-native hardware construction and simulation product.
It contains two version-locked components:

- **LunaWire** is an embedded hardware construction language. A MoonBit
  elaboration program builds a validated, canonical RTL graph.
- **LunaWave** is the deterministic reference simulator and source-level debug
  environment for that graph.

The first reference design is **FluxTile-0**, a host-attached tensor
accelerator used to prove the complete path from construction through
simulation, standard RTL, synthesis, FPGA execution, and—only if independently
validated—physical implementation.

LunaChip is not initially a general SystemVerilog implementation, CPU, SoC,
GPU, foundry service, or production inference accelerator.

## Why one repository

LunaWire and LunaWave share one semantic contract and one canonical IR. A
language change is incomplete until its reference simulation, validation,
serialization, and standard-RTL behavior change together. They therefore use
one repository, one version, one compatibility policy, and one phase gate.

User-facing names remain distinct because they describe different jobs; they
are not independently releasable products.

## Ownership boundary

LunaChip owns:

- hardware generator APIs and elaboration;
- canonical hardware IR and deterministic serialization;
- width, driver, cycle, hierarchy, clock, reset, and memory validation;
- reference simulation semantics and waveform/debug evidence;
- SystemVerilog emission and optional CIRCT interchange;
- assertions, assumptions, cover points, and formal-flow export;
- reference accelerator designs and their software-visible device contract;
- conformance fixtures for third-party simulation and synthesis tools.

LunaChip does not own:

- model loading, tokenization, batching, KV-cache management, or inference
  scheduling;
- node placement, deployment, fleet reconciliation, or model-as-a-service;
- logic synthesis, FPGA place-and-route, ASIC place-and-route, PDKs, SRAM/IO
  macros, packaging, fabrication, or production qualification;
- arbitrary SystemVerilog parsing or simulation;
- a MoonSuite-wide shared hardware IR.

## Product integration boundary

LunaFlux may implement an external adapter for a published LunaChip device ABI.
LunaChip must not import LunaFlux. LunaNexa sees only the generic hardware
capability reported by a LunaFlux runtime; it does not consume LunaWire IR,
LunaWave traces, device commands, registers, or RTL.

```text
LunaNexa -> LunaFlux runtime -> LunaFlux-owned LunaChip adapter -> device ABI

LunaWire generator -> canonical IR -> LunaWave
                                  -> SystemVerilog -> external EDA tools
```

No LunaNexa or LunaFlux schema may enter LunaChip core packages. No LunaChip
elaboration or simulator type may enter their public contracts.

## Public artifact contract

Each released design may publish:

- canonical IR plus schema version and content digest;
- deterministic, human-readable SystemVerilog;
- source map from emitted RTL back to generator and IR locations;
- properties and formal harness inputs;
- device ABI manifest, register map, command layout, and capability manifest;
- LunaWave stimulus, expected results, trace schema, and replay bundle;
- tool lockfile recording versions and hashes used for independent checks;
- evidence manifest listing exactly which gates passed.

An artifact is reproducible only when identical inputs, LunaChip version,
configuration, and target profile produce byte-identical canonical IR. Backend
text may change only under a backend-version change or an explicitly recorded
normalization change.

## Evidence levels and allowed claims

The following levels are cumulative and must never be conflated.

| Level | Required evidence | Allowed wording |
|---|---|---|
| Constructed | LunaWire elaborates and structural validation succeeds | “Elaborates” or “constructs” |
| Simulated | LunaWave tests pass for recorded stimuli | “Simulated in LunaWave” |
| Differentially simulated | LunaWave and a pinned independent simulator agree | “Differentially validated” |
| Formally checked | Named properties pass a pinned formal task and bound/engine is recorded | “These properties passed…” |
| Synthesized | A named tool maps RTL to a target library or FPGA family and reports results | “Synthesizes for…” |
| FPGA demonstrated | A bitstream ran on a named physical board with captured evidence | “Demonstrated on FPGA…” |
| GDS produced | A named RTL-to-GDS flow completes and its reports are archived | “GDS generated by…” |
| Signoff checked | Named DRC/LVS/timing checks pass under named decks/corners | “Passed the listed checks…” |
| Fabricated | A foundry manufactured physical dies | “Fabricated” |
| Silicon validated | Packaged devices were measured using a published test procedure | “Measured on silicon…” |

A simulator screenshot is not FPGA evidence. FPGA execution is not ASIC
evidence. GDS generation is not fabrication. Fabrication is not functional,
timing, yield, power, or performance validation. A PDK/tool success is not a
foundry signoff unless the foundry explicitly says so.

## Initial supported semantic subset

The first stable subset is intentionally narrow:

- finite-width two-state and known-mask digital values;
- explicit combinational operations;
- single-driver wires;
- edge-triggered registers;
- synchronous memories with explicit port and collision policies;
- explicit clock and reset domains;
- static module hierarchy and elaboration-time parameters;
- ready/valid interfaces;
- immediate clocked properties;
- single-clock reference simulation first, deterministic multi-clock later.

Analog behavior, transistor simulation, delays, tri-state internal fabrics,
power intent, metastability modeling, timing simulation, and arbitrary HDL
foreign modules are not part of the first stable semantics.

## Compatibility

- Canonical IR carries an explicit schema version.
- Device ABI carries independent major/minor versions.
- Serialized artifacts are accepted only when their schema and required
  capabilities are supported.
- Unknown required fields fail closed; unknown declared optional metadata may
  be preserved.
- Compatibility migrations are explicit, pure transformations tested with
  golden fixtures.
- Deprecated public APIs remain for at most one declared release window.
- Experimental IR operations never appear in stable artifacts without an
  experimental capability marker.

## Safety and determinism

LunaChip rejects rather than guesses:

- zero, negative, unresolved, or unsupported widths;
- multiple or missing required drivers;
- implicit truncation, extension, or signedness conversion;
- combinational cycles;
- ambiguous reset or memory behavior;
- cross-domain state transfer without an explicit CDC primitive;
- nondeterministic iteration affecting names, IDs, serialization, or behavior.

Host-language conditionals choose which hardware is elaborated. Hardware
conditionals create explicit multiplexing or guarded assignments. These worlds
must not be silently interchangeable.

## Success definition

The first product proof is complete when a MoonBit-defined 8×8 INT8 systolic
accelerator:

1. elaborates to stable canonical IR;
2. runs deterministic matrix workloads in LunaWave;
3. agrees cycle-for-cycle with emitted SystemVerilog under pinned Verilator;
4. synthesizes under pinned Yosys;
5. passes named FIFO, bounds, protocol, and control properties;
6. publishes a versioned command/device ABI that an external LunaFlux adapter
   can target;
7. makes no FPGA, GDS, fabrication, or silicon-performance claim unless the
   corresponding evidence level has separately passed.
